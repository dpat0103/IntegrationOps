About this project

Understanding the health of external API connections.

IntegrationOps is an independent backend engineering project. It checks the services an application depends on and keeps a clear record of failures and recovery.

The problem

An online store can load normally while its payment service is unavailable. Shipping requests might be too slow, or an identity service might reject an expired access token.

Checking whether the store itself is online does not explain those failures. Each connection needs its own checks and history.

IntegrationOps records what the service returned, classifies the result, and opens an incident when failures persist.

What you can see in the demo

  • Three independent example services: payment, shipping, and identity.
  • Normal, slow, and failed responses with readable explanations.
  • An incident opening after repeated failures and resolving after normal responses return.
  • Check history, response times, and an incident timeline for each service.
  • An “Out of date” state when expected checks stop arriving.

Each visitor has separate demo state. All provider responses are simulated.

The engineering behind the interface

The main design question is whether monitoring state stays correct when work is retried, workers overlap, or a process restarts.

  • Persistent check runs: a scheduled check receives a stable ID before entering the queue. Retrying the run reuses its result and does not repeat incident updates.
  • Atomic claims: the database coordinates active runs and expiring leases. One service can have only one queued or running check at a time.
  • Incident consistency: check results, incident changes, and notification records commit together. A database constraint permits only one open incident per service.
  • Durable alerts: notification delivery retries independently. An unavailable Slack webhook does not discard the incident.
  • Monitoring freshness: service results and process heartbeats show whether the monitor is still collecting evidence.
  • Safe configuration: real monitoring changes require operator credentials. Public controls only affect the visitor's simulated services.

How to interpret the results

Working: the response matches the expected status and data, within the response-time threshold. Slow: the response is valid but takes longer than expected. Failed: the check times out, cannot connect, or receives an unacceptable response. Out of date: no recent check arrived within the expected interval plus a grace period.

The default incident policy opens after three consecutive failed checks and resolves after two consecutive Working checks. Slow responses do not resolve an incident.

Successful-check percentage includes valid slow responses. It describes the recorded checks over 24 hours, rather than guaranteed continuous uptime.

Scope & limitations

This is a portfolio project with controlled failure experiments. It is not a commercial monitoring service and does not automatically repair external providers or infer their internal root cause.

External notification delivery is at-least-once: a retry can repeat a message if delivery succeeds immediately before a worker crashes. Retention limits historical detail; the latest result is preserved. Production deployment also needs appropriate HTTPS, secrets, egress controls, and operational ownership.

Test results, experiment settings, and measured limitations are kept in the repository so technical claims can be checked.
